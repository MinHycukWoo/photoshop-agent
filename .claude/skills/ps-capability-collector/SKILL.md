# 기능 정보 수집관

프롬프트 정보 수집관(`prompt-collector`)이 "어떻게 말할지"를 모은다면,
이 수집관은 **"포토샵을 MCP 로 어디까지 조종할 수 있는지"** 를 모은다.
결과(`knowledge/ps-capabilities.md`)는 다음 도구를 고를 때(2단계 · 작은 정리) 근거 자료로 쓴다.

> 이 스킬은 **문서만** 만든다. `mcp-server/`, `ps-plugin/` 코드는 수정하지 않는다.
> 실제 도구로 만들지는 사용자와 따로 정한다.

## 1. 범위 정하기
- 사용자가 기능 영역을 말했으면 그것만 (예: "텍스트 레이어", "선택 영역", "필터", "내보내기").
- 말이 없으면 `knowledge/ps-capabilities.md` 의 "수집 기록" 표를 보고 **아직 비어 있는 영역**을 고른다.
  영역 목록: 문서 · 레이어 · 선택 · 변형 · 조정/필터 · 텍스트 · 마스크 · 생성형 AI · 내보내기/파일 · 액션/스크립트 · 앱 정보/이벤트 · 다른 MCP 서버 조사
- 처음 실행(문서가 없거나 비어 있음)이면 **"다른 MCP 서버 조사" + "생성형 AI"** 부터 한다.
- 이번 범위를 사용자에게 한 줄로 알리고 진행한다.

## 2. 지금 우리 도구 파악 (매번)
- `mcp-server/src/index.ts` 의 `register("ps_…")` 이름과 `ps-plugin/main.js` 의 `handlers` 를 읽어 **이미 있는 기능**을 확인한다.
- 문서 맨 앞 "현재 우리 도구" 표가 실제 코드와 다르면 고친다.

## 3. 조사
- 출처 우선순위:
  1. **Adobe 공식** — Photoshop UXP API 문서(developer.adobe.com/photoshop/uxp), batchPlay 문서, Photoshop 도움말, Adobe 공식 MCP/에이전트 발표가 있으면 그것
  2. **공개된 다른 Photoshop MCP 서버** — GitHub 저장소의 README·도구 정의(소스의 tool name·description). 별·최근 커밋 날짜도 적는다
  3. 개발자 포럼(Adobe Community / UXP 포럼)·블로그 — 여러 곳에서 **반복 확인되는** 내용만
- WebSearch 는 `standard` 로 여러 개를 한 번에, 핵심 페이지는 web-fetch 로 직접 읽는다. GitHub 은 `gh` CLI(`gh repo view`, `gh api repos/…/contents/…`)로 읽어도 된다.
- 막힌 출처(403 등)는 다시 시도하지 말고 수집 기록에 남긴다.
- 다른 저장소 코드를 **복사해 쌓지 않는다.** 도구 이름·하는 일·방식(DOM / batchPlay / ExtendScript / 기타)만 자기 말로 요약한다.

## 4. 판단 규칙 (중요)
- **batchPlay descriptor 는 추측해서 적지 않는다.** (프로젝트 규칙) 문서에서 본 것이면 출처를 달고, 아니면 "녹화 필요(Action 녹화 → 복사)"라고만 적는다.
- 각 기능에 **근거 등급**을 단다:
  - `[공식]` Adobe 문서에 API 로 나와 있음
  - `[다른 MCP]` 공개 MCP 서버가 구현해 둠 (동작은 미확인)
  - `[커뮤니티]` 포럼·블로그 보고
  - `[검증됨]` 우리가 이 PC(Photoshop 버전 명시)에서 직접 돌려 봄 — `docs/progress/` · `experiments/` 근거가 있을 때만
- 각 기능에 **우리 프로젝트 적합도**도 단다: 
  - 방식: DOM API / batchPlay / 둘 다
  - 크레딧: 생성형 크레딧 소모 여부
  - 위험: 되돌리기 어려움(저장·덮어쓰기·닫기), 모달 창이 뜨는지(모달이면 모든 명령이 막힘 — 5단계 경험)
  - 최소 버전: 알 수 있으면 (현재 우리 PS 버전은 `ps_status` 또는 기록 기준)
- ExtendScript(JSX)·CEP 전용 기능은 UXP 플러그인에서 바로 못 쓸 수 있다 — "UXP 대체 필요"로 표시한다.

## 5. 문서 형식
`knowledge/ps-capabilities.md` 는 아래 형식을 지킨다 (나중에 `knowledge.ts` 의 `loadSections` 로 RAG 에 붙일 수 있게 prompt-patterns 와 같은 모양).

```markdown
## 영역 이름 (예: B. 레이어)

### 기능 이름
- 키워드: 한국어 표현 여러 개, 영어 API 이름
- 근거: [공식] / [다른 MCP] / [커뮤니티] / [검증됨]
- 하는 일: 한두 줄
- 방식: DOM `app.activeDocument.layers…` / batchPlay `_obj: "…"` (출처 있을 때만) / 녹화 필요
- 크레딧: 없음 / 생성형 크레딧 소모
- 위험·제약: 모달 여부, 되돌리기, 최소 버전 …
- 우리 상태: 있음(`ps_…`) / 없음 / 후보(추천 이유 한 줄)
- 출처: URL · URL
```
- 기존 항목과 겹치면 새로 만들지 말고 **기존 항목에 출처·정보를 보탠다.**
- "다른 MCP 서버" 영역은 서버마다 하나의 `###` 로: 저장소 URL · 별 · 마지막 커밋 · 방식 · 도구 목록(이름 + 한 줄) · 우리에게 참고할 점.
- 맨 아래 **"도구 후보 순위"** 표(기능 · 왜 쓸모 · 난이도 · 크레딧 · 근거)를 갱신한다 — 사용자가 다음에 만들 도구를 고르기 쉽게.
- 맨 아래 **"수집 기록"** 표에 날짜·범위·비고(막힌 출처 등) 한 줄 추가, 맨 위 "마지막 수집" 날짜 갱신.

## 6. 확인
- 문서의 모든 항목에 출처가 있는지, `[검증됨]` 은 실제 근거 파일이 있는지 훑어본다.
- "현재 우리 도구" 표가 `index.ts` 와 맞는지 다시 확인한다.

## 7. 마무리
- 사용자에게 한국어로 보고: 새로 찾은 기능 · 다른 MCP 서버 요약 · **도구 후보 상위 3개와 이유** · 막힌 출처.
- 후보를 실제로 만들려면 batchPlay 녹화부터 해야 한다는 점(필요한 경우)을 안내한다.
- 사용자가 원하면 커밋한다 (README 진행 상황은 바꾸지 않는다. 수집 기록은 문서 안에 남는다).
